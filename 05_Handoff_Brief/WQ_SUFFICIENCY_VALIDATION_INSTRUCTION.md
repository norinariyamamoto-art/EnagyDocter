# Energy Doctor｜WQ単位情報充足率・Threshold Validation 指示

Energy_Doctor_Design_Issue_Log.md（最新）を読んでください。ED-DI-003は
「Implemented / Pilot Threshold & Granularity TBC」状態です。

今回は、情報充足率の集計粒度としてWQ単位を第一候補とし、閾値40%/50%/60%の
どれが妥当かをS社が判断するための比較データを作る「検証」タスクです。
正式な粒度・閾値をこの場で決定・実装確定するものではありません。
正本ファイル（V2.2/V2.3、Forms実装仕様）は変更しないでください。
ED-DI-001（Unknown表示文言）には一切触れないでください。今回のスコープ外です。

## やること

### 1. 情報充足率をWQ単位で再計算する（既存のトップレベル項単位とは別に）

現行の`weighted_score()`が返す`information_sufficiency`は、AVERAGEブロック単位
（トップレベル項単位）です。これとは別に、WQ単位の情報充足率を計算する関数を
新設してください。定義は次のとおりです。

  WQ単位の情報充足率 = 回答済みWQの有効ウェイト合計 ÷ 当該KPI対象WQの全ウェイト合計

Unknown（UNKNOWN正規化後）のWQは分子に含めません。

**重要：有効ウェイトは「ユニークなWQの集合」に均等配分するのではなく、現行Web
KPI算定式（web_kpi.pyの各weighted_score()呼び出し）の各トップレベル項をそのまま
展開して算出してください。** 各トップレベル項の重みを、その項に含まれるWQの数で
均等分割したものを、そのWQの「その項からの寄与ウェイト」とします。**同一WQが
同一KPI内の複数の項に登場する場合は、その各項から配分されるウェイトを重複排除
せず累積してください。** 既知のISS-04（WQ-403がWeb_DRIの0.15項と0.10項の両方に
登場する二重加重）はHOLDのため、今回の検証で重複排除・補正しないでください。
現行KPI算定式の構造をそのままWQ粒度へ展開したものが、今回の情報充足率です。

もしこの均等分割以外のより適切な重み付けが正本から読み取れるなら、根拠を示した
上でそちらを使っても構いません。

KPI点数本体の計算方法（Unknownを除外し残存ウェイトを再正規化する既存の
weighted_score()）は変更しないでください。今回追加するのは、点数計算とは独立した
「WQ単位の情報充足率」という新しい指標です。既存のトップレベル項単位の
information_sufficiencyも、比較のため削除せず残してください。

### 2. Web_EDI/Web_DRI/Web_EPIそれぞれ独立に判定する

3つのKPIそれぞれについて、WQ単位の情報充足率を個別に算出してください。
一部のKPIだけ情報不足になり得ることを前提にしてください（例：Web_EDIは十分でも
Web_EPIだけ情報不足、というケースがあり得ます）。

### 3. 閾値40%/50%/60%での判定結果を比較できるようにする（Validation専用）

各KPIについて、WQ単位の情報充足率が40%/50%/60%それぞれの閾値と比較して
どう判定されるかを、3閾値同時に出力・比較できる形にしてください。判定条件は次で
統一してください。

  WQ information sufficiency >= threshold → OK
  WQ information sufficiency < threshold → INSUFFICIENT_DATA

**今回の40%/50%/60%判定はValidation専用の比較出力です。Engine Patch 2で実装済みの
本番diagnosis_status、仮Threshold 0.5、Pipelineの既存判定ロジックには接続しないで
ください。** 正式な粒度・Thresholdが決定された後、別途Pipelineへ反映します。
比較結果の出力は、例えば次のような専用フィールドで構いません。

  wq_sufficiency_edi / wq_sufficiency_dri / wq_sufficiency_epi
  status_at_40 / status_at_50 / status_at_60（EDI/DRI/EPIそれぞれ）

既存のPipelineResult.diagnosis_statusや、pipeline.pyのMIN_INFORMATION_
SUFFICIENCY_THRESHOLD_TBC（0.5）は変更しないでください。

### 4. 次の6パターンの境界ケースを作成し、TC-A/B/C・Task2の5シナリオとは別に
   専用のテストデータとして機械試験してください

1. 全WQ回答済み → 充足率100%、`OK`
2. 約75%回答 → 原則`OK`（40/50/60%いずれの閾値でもOKになることを確認）
3. 約60%回答 → 40/50/60%閾値での判定の境界比較
4. 約50%回答 → 50%閾値での判定境界確認
5. 約40%回答 → 40/50/60%で判定が分かれることを確認
6. 重要WQ（Web_EPIに使われる緊急度・影響系のWQなど）を中心にUnknownにし、
   他は回答済みにする → 単純な「回答数の割合」だけでなく、特定のKPIだけが
   情報不足になるか、Guardrail pending / review_itemsとの整合が取れているかを
   確認する

**WQごとの有効ウェイトは均一とは限らないため、ちょうど40%/50%/60%を作れない
場合があります。** その場合は、各閾値の直下・直上となる、実際に構成可能な最も
近いケースを使用し、実測の充足率をそのままレポートしてください（無理に
ちょうどの値へ丸めないでください）。

各パターンについて、Web_EDI/DRI/EPIそれぞれのWQ単位情報充足率の実測値と、
40%/50%/60%それぞれでの判定結果（OK / INSUFFICIENT_DATA）を一覧化してください。
